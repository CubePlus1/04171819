# 03 · Echo 详细分析

> `dundao-echo` / `feat/dundao-echo` · 加权总分 **6.48** · 状态：**冻结**

## 形态速览

单列对话式纸面 demo：
- 打开页面后 AI 自动 SSE 流入对话气泡
- 每 8 秒一轮 · 用打字机效果展示"她想起了这件事"
- 最终气泡展开为"明信片"形态
- MindCanvas 放在对话流上方作为念头图谱

技术栈（刻意做极简对照）：
```
后端：原生 Node http + SSE + in-memory
前端：React + 原生 CSS（零 Tailwind / 零 Zustand / 零 Framer Motion）
测试：smoke + echo.test + caps.test + ambient.test
```

10 轮 codex review 同等打磨过 · 91/100 final go-no-go。

## 最强点

### ★ 情感浓度最高

- 纸面质感 · 奶白背景 + 衬线字体（Noto Serif SC）
- "她曾经放不下的"印章效果
- 打字机气泡 · 一字字浮现
- 最终明信片 · 不是卡片 · 是一封信

Echo 在**情感层面**比主 demo 强半档。

### ★ 技术栈最轻

- 零依赖框架（没 Express、没 Tailwind、没 Zustand、没 Framer Motion）
- 原生 CSS 动画 · 原生 fetch 读 SSE · 原生 Node http
- 代码最少 · 风险最低 · 最容易迁移

### ★ 零输入 · 最"被动"

连 trigger picker 都没有 · 打开即开始。
用户只需要看 · 什么都不用做。

### ★ 技术层面等同成熟

10 轮 codex review 全部通过：
- AbortController 传参取消
- CORS origin allowlist
- per-IP / 全局并发流上限
- 原生 CSS reduced-motion 支持
- SIGTERM 活跃流下 <3s 优雅退出

和主 demo 同等的工程质量。

## 最致命的问题

### ★★★ 形态违背赛道三核心原则

赛道三原题：
> "创造一种新的**信息流内容单元** · 像信息流中的下一条内容一样成立"

Echo 的形态：
- 打开页面 → 看到一页 **聊天气泡线程**
- 评委的大脑第一反应：**这是 AI 陪伴 App / 聊天机器人**
- 赛道三题面明确反对"传统工具"形态 · 陪伴 App 就是传统工具

这不是 pitch 可以修补的问题。
这是**形态层面的结构性错位**。

### 为什么这个弱点无法翻盘

对比主 demo 的"双面板质疑"：
- 主 demo 的右面板是**装饰性补充** · 左面板本身是核心产出
- 改成单面板后产品依然成立（左面板就是完整 demo）

对比 Echo 的"形态错位"：
- Echo 的**整个产品就是对话流**
- 改成"卡片"就不是 Echo 了 · 是完全重写

这是层级差别。

### 用户访问路径违反"被动刷到"

赛道三要"被动刷到即成立"：用户在刷信息流时突然遇到。

Echo 的访问路径是：
1. 用户**主动打开** Echo 网页
2. 开始看 AI 回响

这个"主动打开"的动作**本身违反了赛道三的被动前提**。

## 次要弱点

### 视觉强度弱

对比主 demo 的 12 套可切换主题 + 复杂左右布局 · Echo 只是一页纸面风格 · 展台上视觉吸引力弱。
路人停留 3 秒看一眼 · Echo 可能被误认为"这是个博客页面"。

### 难以系列化

主 demo 的卡片作为"信息流内容单元"天然可以生成 1000 条不同的 · 有系列化想象空间。
Echo 的对话流是**一次性完整阅读** · 系列化意味着"多个对话" · 但那就变成"消息应用"了 · 偏离越来越远。

### 展台演示矛盾

主 demo 站着看几秒能懂 · Echo 需要坐下来看完一个回合（~8 秒 × 3 轮 = 24 秒）。
展台前路人会**走过**而不是**看完**。

## 为什么不符合赛道三

用赛道三评审锚点的 5 个问题检查：

1. **刷到即懂**：❌ 不是刷到 · 是打开
2. **不需要跳转**：✓ 对话流内完成
3. **不需要学习成本**：△ 要理解这是聊天式呈现
4. **极短时间获得满足**：❌ 一轮 8 秒 · 三轮 24 秒 · 不算极短
5. **自然产生一次互动/使用**：△ 没有互动入口（这本来也是设计目标）

**5 条里 2 条红灯** · 其中刷到即懂是赛道三最核心的。

## 保留 Echo 的价值

虽然冻结 · 不代表删掉。Echo 作为**姊妹探索归档**有几个价值：

### 1. 证明选型过程严谨

面试时可以讲：
> "我们做了两个实验 · 主 demo 是信息流卡片形态 · Echo 是对话流形态。
> 决策依据来自赛道三锚点的逐条检查：Echo 的'刷到即懂'没成立。
> 我们**测试过再放弃**，不是没想到。"

这是个好故事 · 展示工程判断力。

### 2. 对照组作用

主 demo 的优势在对照组存在时才最清晰。
"为什么是信息流卡片而不是对话流"这个问题 · 看两个 demo 并排就答了。

### 3. 技术栈对照价值

Echo 的极简技术栈（零框架）证明：
- 履约型内容的核心逻辑**不依赖复杂栈**
- 核心在**产品定义**（履约 / 主题聚合 / 原子声明），不在技术选型

### 4. 情感浓度设计参考

Echo 的"明信片" / "印章" / "纸面" 设计语言比主 demo 更浓。
未来主 demo 的卡片 polish 可以**借鉴 Echo 的质感**（比如 P2 页可以更纸面一点）。

## 展台上如何处理

**不展示 Echo**。展台只展示主 demo。
README 里标注 Echo 为"姊妹探索 · 未采用"。
面试 / 评委问起时：
> "我们有两个实验分支 · 主 demo 和 Echo。
> 最后选主 demo 是因为它物理符合赛道三的'信息流下一条内容'定位。
> Echo 是对话流 · 形态上不符合 · 所以冻结 · 作为选型过程的对照组。"

## 结论

- 加权分：**6.48 / 10**
- 位置：**冻结 · 姊妹探索归档**
- 为什么冻结：形态层面不符合赛道三 · 无法通过 pitch 语言修补
- 保留价值：对照组 / 选型过程证据 / 未来 UI polish 参考
