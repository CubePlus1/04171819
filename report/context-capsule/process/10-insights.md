## Insight A · 赛道选择的权重是动态的

### 观察

同一批报告，用"长期契合"权重读 ≠ 用"游园会体验"权重读。
赛道二在前者下赢，赛道三在后者下赢。

### 一般化

**报告不给答案，权重给答案。**

任何"哪个方向最好"的结论都隐含一个权重假设。
当权重变化时，结论必须同步更新。
这意味着：
- 评估方案时要先问清"为什么选 = 用什么权重在选"
- 报告/分析的价值是**结构化呈现选项**，不是"给答案"
- 权重本身是一个设计选择，值得单独讨论

### 跨项目适用性

- 技术选型（性能 vs 可维护性）
- 产品决策（用户体验 vs 商业变现）
- 团队招聘（技能匹配 vs 文化匹配）

## Insight B · 游园会 AI 展台的结构性困境

### 观察

做"AI 懂你"类展台产品时会遇到一堵墙：

- 观众不是 AI 懂的主体（不是 TA 自己的数据）
- 因此观众无法真正体验"被懂"
- 所有依赖"精准个性化"的方案在展台上失效

### 一般化

**"个性化 AI 产品"在展会/演示场合有结构性展示困境，因为演示场合和使用场合的用户主体不一致。**

大多数方案假装没撞到墙（用一套"预写的 persona 对比"蒙混），本方案选择正视墙。

### 解决模式

当"给 X 的体验"在 X 不在场时失效，需要把体验转移到 X 的旁观者能共享的东西上。具体到本方案：
- 从"懂你" → "懂情境"
- 从"个人" → "共享的此刻"

这是一个**可复用的解题模式**：把"不可旁观的体验"转换成"可旁观的对象"。

### 跨项目适用性

- 任何"AI 助理"类产品的 demo 设计
- "个性化推荐"的发布会演示
- 私密型产品（如心理健康应用）的对外展示

## Insight C · "新数据形式"是比"新 UI"更深的创新

### 观察

新 UI 可以被复制、被简化为动画炫技。
新数据形式定义了一个**可被机器消费、可演化、可组合的范畴**。

### 一般化

**把创新点从"样式层"上移到"数据层"，能获得 3 个额外杠杆：**

1. **复制门槛**：UI 可以截图抄，数据形式需要重做 schema
2. **生态可能**：数据形式可以被其他工具消费，UI 不行
3. **评委记忆**：看到新 UI 说"好看"，看到新数据形式说"这组人在定义东西"

### 案例对标

- Markdown 的成功不在于"好看的排版"，而在于"轻量级的文档数据格式"
- JSON 取代 XML 不是因为 UI 更好，是因为数据格式更简洁
- GraphQL 胜过 REST 不在于请求 UI，而在于"查询是一种新数据形式"

### 跨项目适用性

- 做工具时问"我能不能定义一种新数据类型"
- 做协议时问"这能不能成为一种可被第三方消费的格式"
- 做 API 时问"输出结构本身是不是创新点"

## Insight D · 预言比响应更有戏剧张力

### 观察

**响应式 AI**：你问 → 它答。
观众看不到"懂"发生的瞬间，因为"懂"发生在你问之前的一刹那。

**预言式 AI**：它先知道 → 你到时发现它准备好了。
wow 被前置到"系统先一步"的那个时刻，变得可观察。

### 一般化

**把交互的时间起点从"用户行动" 前置到"系统准备"，能创造 demo 的戏剧张力。**

### 为什么

戏剧需要 **"准备 → 等待 → 揭晓"** 的弧线。
响应式只有"行动 → 结果"，没有等待弧。
预言式引入了等待弧（倒计时 / predicted_moment），让揭晓有期待感。

### 跨项目适用性

- 任何 AI 产品的 demo 设计
- 推送 / 通知类产品的叙事
- 时间相关的服务（订阅、预约、日历）

## Insight E · 双模切换是诚实的折中

### 观察

做"AI + 展台"类产品时有三条路：

| 路 | 观众看 | 评委看 |
|---|---|---|
| 全预计算 | ✅ 炸 | ❌ 戳穿（作弊感） |
| 全真 agent | ❌ 弱（被工程感拖累） | ✅ 认 |
| **双模切换** | ✅ 炸 | ✅ 认 |

### 一般化

**当两个受众需求冲突时，不要强行兼容一套方案。分路，做两个模式，用开关切换。**

这不是"取巧"，是**诚实地承认两个受众的需求是结构性不同的**，需要结构性地分开。

### 为什么被接受

双模切换**不作弊**：
- 观众模式从不声称自己是真 agent
- 评委模式确实跑真 agent
- 切换按钮是透明的（不藏着）

### 跨项目适用性

- 任何"营销演示 vs 技术评审"双受众场景
- "家长会 vs 学生体验"类教育产品
- "投资人 vs 产品经理"类创业 pitch

## Insight F · Brainstorming skill 的效率来自"一次一问"

### 观察

本次推演用了 brainstorming skill，一次一问地推进 Q1-Q6。
每个问题给候选 + 推荐 + tradeoff，用户快速决策。

### 为什么高效

- 不给候选，用户要自己生成 → 慢 + 易跑偏
- 给候选但不推荐 → 用户决策压力大
- 给候选 + 推荐 + tradeoff → 用户只需判断推荐是否对（快）

### 为什么不应对

- 一次多问 → 答案混乱，后面覆盖前面
- 开放问题 → 用户进入 analysis paralysis
- 不给 tradeoff → 用户反复推翻决策

### 跨项目适用性

- 任何需求澄清对话
- 技术方案讨论
- 设计评审

## 使用这些 Insight 的方式

这些 insight 不是"最佳实践清单"，是**思考工具**。
下次遇到类似困境时，用它们作为**提问的起点**：

- "这次选方案的权重是什么？"（Insight A）
- "我的用户在场吗？"（Insight B）
- "我是在 UI 层创新还是在数据层创新？"（Insight C）
- "我能把时间前置到'系统准备'吗？"（Insight D）
- "我是不是在强行兼容两种受众？"（Insight E）
- "我是不是在一次问太多？"（Insight F）
