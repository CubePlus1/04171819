# Round 3 · Security
## Summary
Reviewed the requested backend, extension, frontend, and spec surfaces with focus on `SESSDATA`, loopback exposure, SQLi, XSS, XHR hook isolation, WS payload trust, and extension permissions. One critical issue remains: the backend is not actually loopback-bound and its HTTP/WS origin policy is broader than the spec in `§3` and `§10 R3`, which turns several otherwise-local data flows into remotely reachable ones. I did not find SQL injection in the reviewed files, and I did not find direct XSS sinks in `MyCommentsPanel` or the B 站 badge injector.

## Critical (1)
1. Backend exposure does not match the loopback-only threat model. `demo/backend/src/server.js:43-60` allows `localhost`, `127.0.0.1`, and RFC1918 LAN origins; `demo/backend/src/server.js:299-302` calls `httpServer.listen(PORT)` with no host, so Node will listen on all interfaces rather than only `127.0.0.1`; and `demo/backend/src/events.js:12-16` accepts WS connections when `Origin` is absent because `isOriginAllowed()` returns `true` for falsy origins at `demo/backend/src/server.js:57-60`. Impact: if the machine is reachable on the LAN, `/api/backfill/start`, `/api/my-comments`, `/api/marks`, `/api/reset`, and `/ws` are no longer protected by “localhost only” as required by the spec (`demo/docs/superpowers/specs/2026-04-21-bilibili-tracker-design.md:76-79`, `:499-500`).

## Warning (4)
1. `SESSDATA` is not logged in the reviewed code, but it is still transmitted from the extension popup to the backend in a JSON body at `demo/extension/popup.js:62-67`, then forwarded by the backend as `Cookie: SESSDATA=...` at `demo/backend/src/bilibili.js:117-120`. That is acceptable only if the backend is truly loopback-only. In addition, `demo/backend/src/historyBackfill.js:88-92` and `:395-406` support `--sessdata=...` on the CLI, which weakens the spec’s “memory only, not written to disk” guarantee because shell history and process listings can expose it.
2. WS payloads are over-shared for a channel that has no client authentication. The backend broadcasts raw user comment text and identifiers in `workflow.begin` at `demo/backend/src/server.js:183` and `demo/backend/src/workflow.js:57-63`; historical signal text and video titles in `workflow.step` at `demo/backend/src/workflow.js:85-96` and `demo/backend/src/ambient.js:250-257`; and full card bodies in `card.generated` at `demo/backend/src/server.js:192`, `:238`, and `demo/backend/src/workflow.js:157`. No raw `SESSDATA` is sent, but comment text, `userId`, video titles, AIDs inside card payloads, and card context lines are exposed to every connected WS client.
3. The XHR/fetch hook does not preserve extension-page isolation. `demo/extension/content_script.js:90-103` injects page-scope code, and that code emits a `CustomEvent` with the captured payload at `demo/extension/content_script.js:291-300`; the content script then listens on the same global event name at `demo/extension/content_script.js:86-87`. Any B 站 page script can also subscribe to `dundao:bilibili-comment-add` and read the bridged payload. This does not expose `SESSDATA`, but it does fail the stricter requirement that the monkey-patch should not leak captured user data back into page JS global scope.
4. Extension scope is broader than necessary. `demo/extension/manifest.json:6-10` grants `cookies`, `storage`, `notifications`, and `alarms`, but only `cookies`, `notifications`, and `alarms` are used in the reviewed code; `storage` appears unused. `host_permissions` and content-script matches cover `*://*.bilibili.com/*`, and `all_frames: true` is enabled at `demo/extension/manifest.json:15-21`, which expands the injection surface beyond the minimum needed. There is also a compatibility mismatch with the intended hardening target: extension/backend URLs are hardcoded to `localhost` rather than `127.0.0.1` in `demo/extension/content_script.js:2`, `:357-358`, `demo/extension/service_worker.js:3-9`, and `demo/extension/popup.js:1-2`.

## Info (3)
1. I did not find SQL injection in the reviewed files. All user-controlled values flow through bound parameters, including `INSERT`/`SELECT` calls in `demo/backend/src/ingest.js`, `demo/backend/src/historyBackfill.js`, and `demo/backend/src/server.js`. The only dynamic SQL shape is `/api/marks` at `demo/backend/src/ingest.js:458-478`, where the placeholder count is generated dynamically but the values are first coerced to integers and then passed as positional parameters, so this is not a SQLi sink.
2. I did not find direct XSS sinks in the requested rendering paths. `demo/frontend/src/components/MyCommentsPanel.jsx:70-81` renders DB-backed strings through normal JSX text nodes, not `dangerouslySetInnerHTML`; `demo/extension/content_script.js:465-477` creates the badge with `document.createElement()` and assigns `textContent`, not HTML. The `card_id` is also passed through `encodeURIComponent()` before `window.open()` at `demo/extension/content_script.js:471-474`.
3. `/api/backfill/start` itself does not log the submitted `sessdata` in the reviewed code. The route only trims/validates the field at `demo/backend/src/historyBackfill.js:325-356`, and failure logging records `err.message` / `stack` only at `demo/backend/src/historyBackfill.js:370-379` and `:405-406`. I also did not find any WS frame that includes raw `SESSDATA`.

## Threat Model Quick Check
| Asset | Stored? | Logged? | Transmitted? | Leak Risk |
| --- | --- | --- | --- | --- |
| SESSDATA | Not in app DB/storage; browser cookie plus transient popup/body or CLI arg only | No direct token logging found | Yes: popup -> `/api/backfill/start`; backend -> Bilibili `Cookie` header | High until loopback binding is fixed |
| your mid | No explicit capture/storage found in reviewed code; app uses `demo-user` instead | No | No explicit transmission found | Low |
| video aids | Yes: DB fields and card payloads | Yes, in some debug/warn contexts and WS payloads | Yes: extension -> backend, backend -> frontend/WS | Medium |

## Passed
- No reviewed code path writes `SESSDATA` into SQLite or includes it in WS payloads.
- No reviewed SQL statement interpolates raw user input directly into SQL text.
- `MyCommentsPanel` and the B 站 badge injection path use escaped text sinks rather than HTML sinks.
- `cookies`, `alarms`, and `notifications` permissions are justified by the reviewed implementation; only `storage` currently looks unnecessary.
